# ADR-0001: 单线程心智模型，多线程物理隔离

> 状态: 已接受 | 日期: 2026-07-31

## 背景

egui/eframe 要求 UI 状态（`AppState`、纹理）在主线程创建与访问。图片解码可能耗时数百毫秒，不能阻塞主线程，因此"必须用多线程"，但多线程共享可变状态容易引入死锁、竞态与心智负担（`Arc<Mutex<>>` 层层包裹、锁顺序问题）。

## 决策

- **除图片加载外，一切代码在主线程运行**，包括全部 UI 逻辑与状态变更。
- 多线程代码**物理隔离**在 `app.rs` 的 `spawn_loaders` / `poll_loading` / `poll_drops` / `drain_pending_drops` 方法中，其他模块不得出现线程原语。
- 子线程用完即弃（`std::thread::spawn` + 闭包捕获），不建线程池。
- 线程间只通过 `std::sync::mpsc::channel` 通信，载荷是完整的自有数据（`LoadResult`），不共享引用。
- 全仓库禁止 `Arc<Mutex<>>`、`RwLock`、全局可变状态。

## 后果

- 正面：无锁无竞态，状态变更顺序完全确定；新增功能时不需要思考线程安全；调试容易。
- 代价：主线程不能做重计算，所有重 CPU 工作必须下沉到子线程（见 ADR-0003）；无法利用多核做 UI 侧计算（当前无此需求）。
- 风险：`AppState` 变大后容易悄悄引入主线程重计算（如全图遍历），需要在评审时关注。

## 备选方案

- `Arc<Mutex<AppState>>` 共享状态：被否决，违背 egui 主线程模型，且锁粒度难以把握。
- rayon / 线程池：被否决，任务数 ≤ 8（`MAX_IMAGES`）且生命周期短，线程池收益为零，还引入依赖。
