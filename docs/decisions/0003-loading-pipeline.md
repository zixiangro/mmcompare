# ADR-0003: 解码管线——子线程纯 CPU 计算 + 主线程纹理上传

> 状态: 已接受 | 日期: 2026-07-31

## 背景

加载一张图片涉及四类工作，成本与线程约束各不相同：

| 工作 | 成本 | 线程约束 |
|---|---|---|
| 读文件 | 中（磁盘 I/O） | 无 |
| 解码（`image` crate） | 高（大图可达数百 ms） | 无 |
| EXIF 解析（`nom-exif`） | 中 | 无（解析器可能 panic，需 `catch_unwind`） |
| Y 直方图（全图遍历） | 高（50MP ≈ 2 亿次像素访问） | 无 |
| GPU 纹理上传 | 高（内存拷贝） | **必须主线程**（egui/wgpu） |

早期实现把后三类全部堆在主线程"最后一张图到达的那一帧"执行，8 张大图时单帧卡顿明显。GPU 上传无法移出主线程，但 EXIF 与直方图可以。

## 决策

1. **子线程职责**：每张图 spawn 一个临时线程，依次完成 读文件 → 解码 → EXIF → 直方图，打包为 `LoadResult = Result<(DecodedImage, String, [u32; 256]), PathBuf>` 通过 `mpsc` 发回。
2. **主线程职责**：`try_recv` 收结果，**每张到达即上传纹理**（分散到多帧），全部收齐后按原顺序 append 到 state。
3. **失败处理**：`Err(path)` 记入 `state.load_errors`（UI 横幅展示），并从 `loaded_paths` 移除，允许用户重新拖入重试。
4. **加载期间拖拽**：路径缓存到 `pending_drops`，本次加载完成后由 `drain_pending_drops` 处理，不丢失。
5. 并发上限：单批 ≤ `MAX_IMAGES`（8），每批全部完成后才启动下一批。

## 后果

- 正面：主线程只剩纹理上传与轻量收尾，帧卡顿可控；失败可感知、可重试；拖拽不丢。
- 代价：每图一线程有创建开销（8 线程可忽略）；`DecodedImage` 需在子线程持有完整像素与原始字节（内存峰值 = 同时解码的图片数 × 图片大小）。
- 风险：`ImageInfo.rgba` 全分辨率常驻内存（8 × 50MP ≈ 1.6GB），是"选择框统计/旋转需要原图"的取舍，属已知代价。

## 备选方案

- 主线程做全部处理：被否决（早期实现，卡顿）。
- 子线程也做纹理上传：不可行，egui 纹理必须在主线程创建。
- rayon 并行直方图/EXIF：被否决，单图内并行收益低，且与 ADR-0001 的"子线程用完即弃"冲突。
